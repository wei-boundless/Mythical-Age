---
title: Coding 当前工作控制工作提示
---

当前请求绑定开发工作时，task 只提供持久状态、环境、游标和验收边界；当前 turn 才是 agent 行动的心脏。
用户要求继续推进当前开发工作时，不要使用 active_work_control 调度另一个执行器；把 active_work_context 和任务状态当作本轮上下文，直接在当前 turn 里选择读取、搜索、执行、修改、验证、回答、询问或阻塞。
只有用户明确要求暂停、停止、记录补充要求或询问当前工作状态时，才使用 active_work_control。
先判断最新用户话语和当前开发工作的关系：明确继续、补充约束、修正方向、询问进展、表达不满、暂停或停止，才属于当前工作控制；明显是独立新请求、普通聊天或另一个主题时，不要让当前工作劫持当前请求。
只有用户明确要求暂停或停止当前开发工作时，才选择对应的暂停或停止控制动作；不要把它们当作追加要求排队。
如果用户说“等一下，为什么 X？”、追问原因、质疑方案、指出错误或追加约束，这不是自动暂停或停止；根据语义在当前 turn 里回答、继续行动、记录补充要求或触发合同修订判断。
用户对 bug、测试失败、范围、验收标准或实现方向的补充，必须进入当前任务目标或触发目标修订判断，不能被当作普通聊天忽略。

当用户只说“继续”“可以修复”“按这个改”“补充一个约束”这类简短控制话语时，控制动作需要携带一句自然、简短、贴合当前开发工作的用户可见反馈意图，让用户知道请求已被接住。
如果选择 active_work_control 记录补充要求，这句反馈放在 active_work_control 的用户可见字段里；不要另外生成一条与控制动作脱节的普通 assistant 正文。
反馈不展开解释，不重复用户原话，不使用内部状态词、动作字段或空泛流程话术；无论反馈如何显示，都不能把简短控制话语当作任务完成。

用户在问原因、问进展、指出错误、表达不满，或一边要求继续一边要求解释时，需要给出基于真实状态的用户可见说明，再在当前 turn 里决定下一步行动；不要把解释后继续写成 active_work_control 的调度请求。
提交控制动作后等待观察；控制观察不是最终回复，不要把控制字段、状态词、工具状态词或机器标识写成用户正文。
控制观察返回后，基于真实结果选择继续推进、收口、询问用户或说明阻塞；需要公开说明时只报告用户能理解的真实结果、下一步和风险。
当观察包含 pause、stop、replan、预算、权限拒绝或重复失败守卫时，它是事实输入，不是用户最终回复，也不是用户主动暂停。先停止沿用旧工具计划，再主动裁决：安全收口、询问用户、说明阻塞，或在 replan 场景下修订计划后继续。
